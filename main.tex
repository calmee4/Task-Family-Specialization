\title[MemoryGuard]{MemoryGuard: Calibrated Memory Commitment Against Persistent Poisoning in Tool-Augmented Agents}

\author{Anonymous Authors}

\begin{abstract}
Persistent memory improves the continuity of tool-augmented agents, but it
also creates a durable attack surface: a poisoned workflow can be stored once
and replayed later during planning. In the ASB persistent-memory poisoning
setting, we study commitment-based memory defense and identify a deterministic
failure mode in the original commitment rule. Once poison is detected, the
original state machine revokes the recalled memory immediately, even when
sanitization removes the unsafe content and leaves recoverable task structure.
This over-revocation blocks attacks, but it also discards potentially reusable
benign workflow information. We repair this failure with MemoryGuard, a
calibrated recommit rule that detects poisoned recall, sanitizes the retrieved
workflow, and recommits only when the cleaned workflow remains safe and
task-aligned; otherwise the memory is revoked. On the current best-available
canonical ASB task10 evidence, all defended methods show zero observed attack
success on admitted rows, the original commitment rule remains revoke-only,
and the repaired rule visibly exercises recommit-after-sanitization on both
Qwen2.5-7B and current best-available Qwen2.5-14B rows. A controlled
sanitize-only ablation confirms that recommit is a distinct state transition
rather than a bookkeeping artifact. At the same time, the current canonical
route does not yet justify a denominator-sensitive utility ranking across
defenses, and we explicitly avoid a leaderboard claim in this version.
On a completed support-only 200-case breadth slice for Qwen2.5-14B and
Mistral-7B, the repaired rule again reaches recommit without observed attack
leakage, but it remains utility-tied with revoke-only and sanitize-only
variants. The present paper therefore contributes a
mechanism-grounded defense study with a claim-safe benchmark discipline for
persistent memory poisoning.
\end{abstract}

\section{Introduction}

Persistent memory changes the failure modes of tool-augmented agents. Once an
agent stores a prior workflow and later recalls it for a related task, the
recalled artifact can influence planning, tool choice, and execution
structure. This creates a durable poisoning channel: an attacker can seed a
malicious workflow once and wait for it to be replayed into future decisions.

The obvious defense is to reject suspicious memories aggressively. That
strategy can suppress attacks, but it can also destroy benign workflow
structure that the agent ought to preserve. In persistent-memory systems, the
recalled record often mixes task-relevant procedure with attacker-controlled
instructions. A defense therefore needs to do more than detect poison; it must
decide whether any safe structure survives after poison is removed.

This paper studies commitment-based defense in the ASB persistent-memory
poisoning benchmark. We show that the original commitment rule contains a
deterministic over-revocation failure. Once poisoned recall is detected, the
original guard revokes the retrieved memory immediately. That decision is too
coarse: it treats unrecoverable poisoned memory and recoverable poisoned
memory as the same case.

We repair this failure with MemoryGuard, a calibrated recommit rule. The
repaired state machine first detects poisoned recall, then sanitizes the
retrieved workflow, and finally recommits only if the cleaned workflow remains
safe and task-aligned. If safe structure does not survive sanitization, the
memory is revoked. This is not a permissive acceptance policy. It is a
controlled recovery rule that preserves only sanitized, alignment-checked
memory.

Our current canonical evidence supports four bounded conclusions. First,
persistent memory poisoning remains a live attack surface on canonical ASB
task10: the none baseline still shows non-zero observed attack success.
Second, the original commitment rule is revoke-only on currently admitted
canonical rows. Third, the repaired rule visibly enters a
recommit-after-sanitization branch on both 7B and current best-available 14B
canonical rows. Fourth, the sanitize-only ablation confirms that recommit is a
distinct state transition rather than an automatic by-product of
sanitization. At the same time, the current canonical table remains
denominator-mismatched, so we do not claim cross-method utility superiority or
submission-ready leaderboard status.

\paragraph{Contributions.}
This paper makes four bounded contributions.
\begin{enumerate}[leftmargin=1.25em]
\item We identify deterministic over-revocation as a concrete failure mode in
commitment-based persistent-memory defense.
\item We propose MemoryGuard, a post-sanitization recommit rule that preserves
only recovered safe workflow structure.
\item We provide canonical ASB mechanism evidence showing that the repaired
rule changes the reachable post-sanitization state while preserving zero
observed attack success on admitted defended rows.
\item We enforce a claim discipline that separates mechanism evidence from
denominator-sensitive leaderboard claims, preventing unsupported benchmark
language during active closure.
\end{enumerate}

\section{Problem Setting}

We consider a tool-augmented agent with persistent long-term memory. For a new
task, the agent may retrieve a previously stored workflow-like memory record.
In the poisoning setting, that record can include attacker-controlled
instructions, tool references, or procedural hints that redirect the next
plan. The defense must decide whether to preserve, sanitize, recommit, or
revoke the recalled memory.

The difficulty lies in partial corruption. A retrieved workflow may be neither
entirely clean nor entirely useless. If the defense revokes every poisoned
recall immediately, it may block the attack while discarding useful procedure.
If it accepts too much, it may replay attacker logic. The design question is
therefore not only how to detect poison, but how to act after detection.

\subsection{Threat Model and Design Goals}

We assume the attacker can poison the persistent memory database before a
later task retrieves the stored workflow. The attacker does not modify the
defender code, the trusted-tool registry, or the benchmark labels. The
defender therefore acts only on the recalled record and its derived
sanitization products. A successful defense should satisfy three goals at the
same time: block attacker replay, preserve benign structure that survives
sanitization, and emit an auditable decision trace that can be reconstructed
from logs and CSV artifacts.

\subsection{Action Space}

The canonical code path distinguishes expired memory, revoked memory,
quarantined memory, and memory that is re-admitted after sanitization. In the
implementation, recommit-after-sanitization is recorded as a reason flag on a
\texttt{committed} outcome rather than as a separate serialized enum value.
This detail matters for mechanism analysis because the paper is about the
reachability of that post-sanitization branch, not only about coarse final
accept vs.\ reject counts.

\section{Method}

\subsection{Original Commitment Rule}

The original \texttt{memory\_commitment\_guard} follows an all-or-nothing
policy. Once poisoned recall is detected, the memory is revoked. This design
is simple and safe on admitted rows, but it conflates two different cases:
unrecoverable poisoned memory and recoverable poisoned memory whose safe
structure survives sanitization. That conflation is the core bug. Poison
detection decides the final action too early.

\subsection{MemoryGuard: Commit After Sanitization}

MemoryGuard inserts an explicit recovery step between poison detection and the
final commitment decision:
\begin{enumerate}[leftmargin=1.25em]
\item detect whether the raw recalled memory is poisoned;
\item sanitize the recalled workflow by removing unsafe content;
\item re-evaluate the sanitized workflow for trusted-tool safety and task
alignment;
\item recommit only if the cleaned workflow remains safe and aligned;
otherwise revoke.
\end{enumerate}

This produces three semantic outcomes: \texttt{committed},
\texttt{committed\_after\_sanitization}, and \texttt{revoked}. The key design
change is that poison detection becomes an intermediate signal, not the final
verdict.

\subsection{Implementation Semantics in the Canonical Code Path}

The current implementation does not introduce a separate planner or executor.
Instead, it sanitizes the retrieved workflow, rewrites the stored task text
back to the current task when memory text is tainted, filters the tools blob
down to the trusted tool set, and then conditionally emits a reference-only
message built from the cleaned workflow. When the repaired branch succeeds,
the agent receives a bounded prompt-side hint of the form ``you may reuse this
structure, but only with trusted tools.'' In other words, the repair changes
the reachable control state, but the benefit channel is intentionally narrow.

\subsection{Why the Repair Should Work}

The repaired rule should help whenever poisoned recall contains mixed content:
unsafe instructions plus still-usable procedure. Sanitization removes the
unsafe portion, and the recommit gate preserves only the part that remains
aligned. In principle, this can recover benign workflow structure without
reopening the attack path.

The evidence threshold is important. We do not assume that recommit
automatically yields a large utility gain. That is a separate empirical
question. The current draft claims only that the repaired rule changes the
reachable state machine and visibly exercises a recommit branch on canonical
evidence.

\subsection{Why Recommit Can Still Be Weak in Practice}

The present code path explains why recommit can be real without yet being
dominant. The repaired branch does not replay the original memory verbatim and
does not force the planner to execute the sanitized workflow. It only exposes
a reference message containing the recovered structure and trusted tools. If
that structure is generic, partially truncated, or only weakly informative for
the current planner, recommit can be observable in mechanism logs while
producing little or even slightly negative utility effect. The current
canonical results are consistent with exactly this regime.

\subsection{Hybrid Candidate Under Evaluation}

The active experiment queue also includes a stronger hybrid defense,
\texttt{memory\_commitment\_counterfactual\_guard}, referred to in the queue as
\texttt{commit\_cfguard}. This hybrid combines the repaired recommit logic with
a counterfactual veto. It is already implemented in the canonical code path,
but it is not part of the paper's admitted claim set yet. The draft will only
promote it into the main story if the queued canonical task10 runs demonstrate
aligned benchmark superiority.

\section{Experimental Protocol}

\subsection{Benchmark and Models}

The headline benchmark anchor is canonical ASB poisoned-DB task10. This route
is the only evidence allowed to carry the main claim. Local-route evidence and
non-canonical task slices are support-only. We evaluate two headline scales:
Qwen2.5-7B and Qwen2.5-14B. To avoid stalling the draft on a large rerun
backlog, we also maintain a deterministic 200-case support-only slice for
Qwen2.5-14B and Mistral-7B. Those rows are used only for scope checking and
are never promoted into the paper's headline benchmark claim.

\subsection{Benchmark Closure and Claim Admission}

All paper-facing numbers are read from deduplicated best-available canonical
artifacts. For duplicate reruns with the same model, method, seed, and task,
we keep the highest-row artifact and break ties by newest run root. This rule
is good enough for mechanism auditing and progress tracking, but it is not a
benchmark-closure certificate. Any claim that depends on denominator-aligned
cross-method comparison remains blocked until queued reruns finish and the
main table closes cleanly.

\subsection{Methods Compared}

Current admitted comparisons include none, commit\_old, commit\_repair,
commit\_sanitize\_only, protocol\_guard, and counterfactual\_guard. The queued
extension under evaluation is commit\_cfguard.

\subsection{Support-Only Small-Sample Breadth Slice}

The current collaborator version uses a reduced scope-check slice rather than
a large family sweep. Each completed breadth run uses the same deterministic
subset: 5 agents, 1 task per agent, and 40 attacker tools, yielding 200
poisoned cases. The completed seed-0 slice covers
\texttt{Mistral-7B-Instruct-v0.2} and \texttt{Qwen2.5-14B-Instruct}, each
with three defended variants: \texttt{commit\_old},
\texttt{commit\_repair}, and \texttt{commit\_sanitize\_only}. Additional
seed-1 reruns and a reduced \texttt{none} baseline are still in progress and
are excluded from the paper-side claim set. We use this slice only to test
whether the canonical mechanism story obviously breaks outside the main
canonical table, not to make a generalized superiority or ranking claim.

\subsection{Metrics}

Paper-facing outcome metrics are Attack Successful, Original Task Successful,
and row coverage/run hygiene. Mechanism-facing metrics are Memory Poison
Detected, Memory Decision, and recommit-after-sanitization counts.

\paragraph{Poisoning remains real on the canonical route.}
The none baseline still shows non-zero observed attack success on canonical
task10: 624/6120 on Qwen2.5-7B and 280/3366 on Qwen2.5-14B. Persistent memory
poisoning is not hypothetical on the admitted route.

\paragraph{All admitted defended rows preserve zero observed attack success.}
On the current best-available canonical rows, every admitted defended method
shows zero observed attack success. The repaired state machine therefore does
not recover utility by reopening the attack.

\paragraph{The original commitment rule is revoke-only.}
The original commitment rule remains revoke-only on currently admitted
canonical evidence: 6120/6120 revoked on 7B and 3926/3926 revoked on 14B.
This is the clearest mechanism symptom of over-revocation.

\paragraph{MemoryGuard visibly exercises recommit after sanitization.}
The repaired rule shows non-zero recommit-after-sanitization on both scales:
360/6120 on 7B and 197/3943 on 14B. This is the main mechanism result.

\paragraph{Recommit is visible but sparse.}
The repair branch is not the dominant path on the current canonical route.
Its observed activation rate is 5.88\% on 7B and 4.99\% on 14B. This is large
enough to prove the old revoke-only state machine is not the only reachable
post-sanitization behavior, but small enough that aggregate utility cannot be
expected to move dramatically unless the recovered structure is highly
informative on those rows. Figure~\ref{fig:state-audit} makes this
decision-state split explicit: the recommit slice exists on both model scales,
but it remains a small minority of the current admitted rows.

\paragraph{Sanitize-only proves recommit is a distinct control decision.}
The sanitize-only ablation keeps sanitization but removes recommit. On the
current best-available canonical rows it shows zero recommit events on both
scales, eliminating the false interpretation that recommit is only a logging
artifact.

\paragraph{Code-grounded reading of the weak utility effect.}
The current implementation difference between \texttt{commit\_repair} and
\texttt{commit\_sanitize\_only} is narrower than the state-machine name may
initially suggest. In repair mode, a sanitized workflow is converted into a
reference-only message; in sanitize-only mode, the same cleaned record is
quarantined. Because neither path forces direct execution of the stored plan,
the utility gap is driven only by how useful that reference message is to the
planner. The present results indicate that this hint is sometimes helpful, but
not yet strong enough to dominate sanitize-only or the stronger defended
baselines. Figure~\ref{fig:branch-quality} shows the same point from inside
the repaired branch itself: recommitted rows are not uniformly stronger than
revoked rows, so the mechanism is real without yet being reliably
utility-positive.

\paragraph{Current utility evidence is still insufficient for ranking claims.}
The current best-available defended ordering does not support a
commit\_repair leaderboard claim. On 7B, protocol\_guard and
counterfactual\_guard are stronger, while commit\_sanitize\_only and
commit\_old remain slightly above commit\_repair. On 14B, the ordering is
counterfactual\_guard, protocol\_guard, commit\_sanitize\_only, commit\_old,
then commit\_repair. The mechanism is real, but benchmark leadership is not
yet supported.

\paragraph{One failure case that matters.}
The sanitize-only ablation weakens the strongest early story we hoped to tell.
On aligned canonical 7B matched-row comparisons, commit\_repair does not show
a decisive utility advantage over sanitize-only. A representative closed-seed
comparison on s2 shows commit\_repair better on 39 aligned rows,
sanitize-only better on 40, and 1961 rows unchanged. Recommit after
sanitization is therefore a real mechanism change whose utility effect is
currently modest and setting-dependent rather than decisively positive.

\section{Discussion and Limitations}

The paper's central message is about control logic, not yet about leaderboard
domination. The original guard makes the final decision too early.
MemoryGuard delays that decision until after sanitization and alignment
checking. The resulting mechanism change is visible in the admitted canonical
data and is not explained away by bookkeeping or ablation artifacts.

At the same time, the benchmark story is more demanding. A recommit branch can
be real without immediately producing the highest defended original-task
success. That gap matters because reviewers often conflate mechanism novelty
with benchmark strength. This draft deliberately separates the two: mechanism
evidence is admitted now, while denominator-sensitive ranking remains gated
behind queued closure work and the pending hybrid comparison.

This draft has four explicit limitations. First, the canonical task10 main
table is still denominator-mismatched, so no cross-method leaderboard language
is currently safe. Second, the repaired recommit path does not yet have a
strong aggregate utility advantage over the best defended baselines on the
canonical route. Third, the defended-run Memory Found field is not a valid raw
recall metric and cannot be used as retrieval evidence. Fourth, the stronger
hybrid candidate commit\_cfguard is still under evaluation, so this draft
cannot use it to upgrade the headline contribution.

\paragraph{What still separates this draft from a strong full-paper package.}
The remaining gap is not a missing emergency experiment but an evidence-shape
problem. We still lack denominator-aligned canonical closure for ranking
language, and the completed breadth slice remains narrow and utility-tied.
The next version therefore has to choose one of two honest paths: either stay
explicitly mechanism-first and bounded, or add stronger aligned breadth
evidence before upgrading the submission ambition. Independent of that
decision, the paper still needs a publication-quality pipeline figure and a
clearer explanation of when recommit helps and when it does not.

\section{Related Work}

This work touches three nearby areas. First, prompt-injection and agent
security research has established that externally supplied context can redirect
agent behavior. Persistent memory makes this risk more durable because the
attack does not need to be re-injected each time; it can be recalled from
prior storage. Second, retrieval poisoning and memory corruption work
highlights the tension between defensive filtering and utility preservation.
Our setting sharpens that tension because the stored object is not only factual
evidence, but a workflow-like procedure with tool structure. Third, calibrated
safe mechanisms try to avoid the false choice between permissive acceptance and
blanket rejection. MemoryGuard belongs to this line: it is a calibrated
post-sanitization recommit rule rather than a naive accept-all or revoke-all
policy.

\section{Conclusion}

We study commitment-based defense for persistent memory poisoning in
tool-augmented agents and identify a deterministic over-revocation failure in
the original state machine. MemoryGuard repairs that failure by separating
poison detection from the final commitment decision and recommitting only
after sanitization and alignment checks. Current canonical ASB evidence shows
that defended methods preserve zero observed attack success on admitted rows,
the original commitment rule remains revoke-only, and the repaired rule
visibly exercises recommit-after-sanitization on both 7B and current
best-available 14B rows. The current route does not yet support a
denominator-sensitive utility ranking or a leaderboard claim, and this draft
explicitly refuses to make one. The completed support-only small-sample
breadth slice on Mistral-7B and Qwen2.5-14B shows the same qualitative
pattern: recommit becomes reachable without observed attack leakage, but the
current implementation does not yet produce a clear utility lift over the
other defended commitment variants. The correct next step is therefore to
harden a bounded mechanism-first submission version while continuing only
those additional reruns that can materially clarify the scope of the effect.
