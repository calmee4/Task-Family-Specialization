\section{Setup}

\subsection{Official Metric Contract}

\gittaskbench emits official \processmetric and \resultmetric fields for every
graded task result. In the evaluator, missing outputs or test-script failures
are recorded as \processmetric$=$False and \resultmetric$=$False. When a task
reaches the grading stage, the task script writes final \processmetric /
\resultmetric records plus comments, and the result analyzer aggregates those
rows. We keep that contract fixed throughout the paper.

Representative task scripts show why the split is meaningful.
\texttt{Trafilatura\_01} uses $F1 \ge 0.90$.
\texttt{Trafilatura\_02} uses edit-distance ratio $\le 0.50$.
\texttt{SpeechBrain\_05} requires exact JSON \texttt{prediction} match.
\texttt{PDFPlumber\_02} uses a $75\%$ cell-level threshold.
Together, these examples separate reaching grading from meeting the full task
criterion.

Our reported aggregates therefore obey two rules. First, the benchmark-facing
numbers are always the official \processmetric and \resultmetric outputs.
Second, any rates, domain summaries, or heatmaps reported in the paper are
derived only by aggregating those official outputs.
All reported cohorts use GitTaskBench commit \texttt{df188a7}, the same
benchmark prompt/context bundle, and the same single-agent code-generation
loop. Generation is deterministic throughout the study: temperature is fixed at
\texttt{0.0}, each task allows at most two generation/repair attempts, each
attempt is capped at 2600 completion tokens, and generated solve scripts run
under a 240\,s timeout before official grading.

We also interpret \processmetric conservatively. In this paper,
\processmetric$=$True means that the trace advanced far enough to receive an
official benchmark record. It does not mean that every such row is a clean
semantic near-miss: some official comments report threshold misses, while others
report parsing or evaluation errors after grading begins.

\subsection{Cohorts}

The main cohort is a comparable open-model sweep over the full official
\gittaskbench task set. Comparable here means that every model in this cohort
is evaluated on the same benchmark task roster, under the same evaluation
pipeline family, and against the same official evaluator contract. The reported
totals are then computed from the emitted official rows rather than from hand
relabeling.

The open-model roster is:
\begin{itemize}[leftmargin=1.25em]
\item \texttt{Qwen2.5-7B},
\item \texttt{Qwen2.5-14B},
\item \texttt{Qwen2.5-32B},
\item \texttt{Qwen3-14B},
\item \texttt{Qwen3-32B},
\item \texttt{DeepSeek-R1-D8B},
\item \texttt{Mistral-7B},
\item \texttt{Mistral-Small-24B}.
\end{itemize}

To reduce Qwen-centric interpretation, we add a second cohort built from the
shared tasks \texttt{Trafilatura\_01} and \texttt{Trafilatura\_02}. This subset
expands the roster by adding \texttt{gpt-5.2} and
\texttt{Gemini-2.5-Pro}. The task-aligned cohort is smaller, but it lets us
check whether some official success patterns already extend beyond the main
open-model sweep.

For the comparable cohort, each model is evaluated on the full benchmark task
roster. For the shared \texttt{Trafilatura} slice, each model contributes one
aligned run on the same benchmark tasks. This gives broader model coverage, but
it is not comparable in the same sense as the main cohort: it aligns exact
benchmark tasks and the same official evaluator fields, but it is used only as
task-aligned cross-model evidence rather than as a frontier ranking.

We also evaluate a targeted provider cohort for three provider models:
\texttt{gpt-5-chat}, \texttt{gpt-5.2}, and \texttt{Gemini-2.5-Pro}. The task
set is intentionally small but structured. The selection rule is fixed rather
than ad hoc: it includes the main success-bearing families from the comparable
cohort, the main \processmetric$=$True/\resultmetric$=$False families,
and one image plus one video stressor. We report the subset separately rather
than merging it into the comparable totals because it is a targeted subset
rather than a full-benchmark cohort.

We further evaluate a supplementary open-model breadth cohort on the
same subset. Its role is narrower than that of the comparable cohort: it tests
whether the same family concentration persists once the open-model roster is
broadened, while remaining explicitly task-limited.

To test whether that targeted subset extrapolates, we also run
\texttt{gpt-5-chat}, \texttt{gpt-5.2}, and \texttt{Gemini-2.5-Pro} over the
full benchmark under the same evaluation protocol. We likewise report these
runs separately from the comparable cohort and from the targeted provider
cohort.

The paper studies benchmark-visible structure under a fixed evaluation protocol
rather than a synchronized scrape of the public \gittaskbench leaderboard.

\subsection{Aggregation Protocol}

Our aggregation protocol is intentionally simple. Each model-task trace is
first reduced to the benchmark's official \processmetric/\resultmetric pair.
Family labels come directly from the task prefix, e.g., \texttt{Eparse\_02} to
\texttt{Eparse}. Domain labels are then fixed at the family level:
\texttt{Eparse}, \texttt{PDFPlumber}, and \texttt{PyPDF2} are office-document
tasks; \texttt{Faker}, \texttt{InvisibleWatermark}, and \texttt{Stegano} are
security tasks; \texttt{Trafilatura} and \texttt{Scrapy} are web tasks; and so
on. We do not learn a taxonomy from results.

This matters because the benchmark is structurally imbalanced even before model
performance enters the picture. Image tasks occupy the largest share of
evaluation mass, while video is only a small residue. A global pass rate over
this mixture is therefore a blend over very different task families and very
different amounts of evaluation mass.

The same logic explains why we keep the targeted provider cohort separate.
That subset is deliberately curated toward the families that matter most for the
current paper: the main success-bearing families, the main
graded-but-unsuccessful families, and one image/video stress check. It is
therefore useful as a supplementary probe, but it is not a replacement for the
comparable cohort.
Mixing the two into one aggregate would create a reporting problem of its own:
the same paper would conflate a benchmark-wide cohort with a targeted slice.
That distinction matters even more once the targeted subset is multi-model. The
subset is useful for checking whether some cohort zeros disappear under a
different model class, but it should not be mistaken for a replacement
leaderboard.

We use three reporting views throughout the paper:
\begin{enumerate}[leftmargin=1.25em]
\item per-model official totals,
\item domain or family slices aggregated from official outputs,
\item representative official comments from the
\processmetric$=$True, \resultmetric$=$False regime.
\end{enumerate}

This protocol stays within the benchmark's official metric contract while still
recovering more structure than a single global pass rate.

Finally, the protocol is intentionally asymmetric with respect to claims. Global
totals can support only global claims. Family slices can support only family
claims. Representative comments from official outputs can support only scoped
interpretations about the graded-but-unsuccessful regime. We use this asymmetry
throughout the paper to keep the analysis conservative.

We also report exact cohort totals rather than seed-averaged estimates. The
current evidence therefore supports descriptive benchmark claims, not variance
estimates or statistical-significance claims.

\subsection{Analysis Pipeline}

All tables and figures are regenerated from exported summaries of the official
\processmetric/\resultmetric outputs. The analysis therefore does not rely on
manual relabeling or manual transcription. Every reported rate, domain slice,
or heatmap is a deterministic aggregation of the benchmark's own official
outputs.
