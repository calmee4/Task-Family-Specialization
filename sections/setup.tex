\section{Methodology}

\subsection{Official Metric Contract}

As introduced in Section~1, \gittaskbench emits official \processmetric and
\resultmetric fields for every graded trace. Missing outputs or test-script
failures yield \processmetric$=$False, \resultmetric$=$False. When a trace
reaches grading, the task script writes final \processmetric/\resultmetric
records plus evaluator comments.

The split is meaningful because different task scripts impose qualitatively
different criteria. \texttt{Trafilatura\_01} requires $F1 \ge 0.90$.
\texttt{Trafilatura\_02} requires edit-distance ratio $\le 0.50$.
\texttt{SpeechBrain\_05} requires exact JSON \texttt{prediction} match.
\texttt{PDFPlumber\_02} requires $75\%$ cell-level accuracy. These thresholds
separate reaching grading from meeting the full task criterion, and they vary
enough across families that a single global pass rate blends qualitatively
different evaluation standards.

All reported cohorts use GitTaskBench commit \texttt{df188a7}, the same
benchmark prompt/context bundle, and the same single-agent code-generation
loop. Generation uses temperature \texttt{0.0} throughout, each task allows at
most two generation/repair attempts, each attempt is capped at 2600 completion
tokens, and generated solve scripts run under a 240\,s timeout before official
grading. While temperature zero makes the decoding process nominally
deterministic, we note that minor API-level or hardware-level
non-determinism cannot be fully ruled out. We therefore treat the reported
counts as exact single-run observations and avoid claiming statistical
significance from small cell differences.

We interpret \processmetric conservatively throughout the paper.
\processmetric$=$True means that the trace received an official benchmark
record, not that it is a clean semantic near-miss: some official comments
report threshold misses, while others report parsing or evaluation errors after
grading begins. All paper-side aggregates are derived only from these official
outputs; no hand relabeling is involved.

\subsection{Evaluation Cohorts}

We organize the evidence into five cohorts, ordered from the paper's primary
evidence to progressively broader robustness checks:

\paragraph{Comparable open-model cohort (primary evidence).}
Eight models evaluated on the full official \gittaskbench task set through the
same agent harness and evaluator contract:
\texttt{Qwen2.5-7B},
\texttt{Qwen2.5-14B},
\texttt{Qwen2.5-32B},
\texttt{Qwen3-14B},
\texttt{Qwen3-32B},
\texttt{DeepSeek-R1-D8B},
\texttt{Mistral-7B}, and
\texttt{Mistral-Small-24B}.
%
\paragraph{Shared Trafilatura slice (cross-model existence proof).}
Task-aligned runs on \texttt{Trafilatura\_01} and \texttt{Trafilatura\_02} that
extend coverage to \texttt{gpt-5.2} and \texttt{Gemini-2.5-Pro}. This slice
checks whether official success patterns extend beyond the open-model family
but covers only two tasks.
%
\paragraph{Targeted provider cohort (robustness check).}
\texttt{gpt-5-chat}, \texttt{gpt-5.2}, and \texttt{Gemini-2.5-Pro} on a
structured task subset covering the main success-bearing families, the main
\processmetric$=$True/\resultmetric$=$False families, and one image plus one
video stressor.
%
\paragraph{Supplementary open-model breadth cohort (breadth check).}
The same targeted task subset evaluated on additional open-weight models
(\texttt{DeepSeek-R1-Distill-Qwen-32B}, \texttt{Phi-3.5-mini-instruct}, among
others). This tests whether the family concentration observed in the main
cohort persists under a broader roster.
%
\paragraph{Full-benchmark provider sweeps (extrapolation test).}
The same three provider models on the full benchmark, testing whether targeted
subset activations persist once the full task distribution is restored.

\medskip\noindent
The comparable cohort supports the paper's main claims. The remaining four
cohorts are supplementary analyses, each reported in its own section and never
merged into the main aggregate.

\subsection{Aggregation and Reporting}

We distinguish two levels of granularity. A \emph{task family} is the set of
benchmark tasks that share a common software library or tool, identified by the
task-name prefix (e.g., all tasks beginning with \texttt{Eparse} form the
\texttt{Eparse} family). A \emph{domain} is a coarser grouping of families by
the type of data or application they target. Each model-task trace is first
reduced to its official \processmetric/\resultmetric pair, then labeled with
its family and domain.

Domain labels are assigned from the benchmark's own task metadata and library
descriptions rather than learned from model performance. The resulting mapping
is:
\texttt{Eparse}, \texttt{PDFPlumber}, and \texttt{PyPDF2} map to
\emph{office-document} (structured document extraction);
\texttt{Faker}, \texttt{InvisibleWatermark}, and \texttt{Stegano} to
\emph{security} (data generation and steganography);
\texttt{Trafilatura} and \texttt{Scrapy} to \emph{web} (web content
extraction);
\texttt{SpeechBrain} and \texttt{FunASR} to \emph{speech} (audio processing);
\texttt{NeuroKit} to \emph{physiological-signal};
and the remaining families to \emph{image} or \emph{video} by their benchmark
metadata. We fix this taxonomy before examining any results.

This mapping matters because the benchmark is structurally imbalanced. Image
tasks occupy the largest share of evaluation mass, while video is only a small
residue. A global pass rate over this mixture blends very different task
families with very different amounts of evaluation mass, which is why we report
domain slices alongside global totals.

Concretely, we use three reporting views throughout the paper:
\begin{enumerate}[leftmargin=1.25em]
\item per-model official totals,
\item domain or family slices aggregated from official outputs,
\item representative official comments from the
\processmetric$=$True, \resultmetric$=$False regime.
\end{enumerate}

summaries of the official outputs.
