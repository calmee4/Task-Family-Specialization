\section{Related Work}

\paragraph{Repository-grounded agent benchmarks.}
Repository-grounded agent evaluation has grown into a substantial ecosystem.
\texttt{SWE-bench} and \texttt{SWE-agent} test issue-resolution on real GitHub
repositories \cite{swebench,sweagent}; \texttt{SWE-Lancer} and
\texttt{Ambig-SWE} extend that setting to freelance-style and ambiguous
specifications \cite{swelancer,ambigswe}; and long software-task evaluations
stress sustained multi-step execution \cite{longsoftwaretasks}. Broader agent
benchmarks span web interaction \cite{webarena,visualwebarena}, mobile control
\cite{androidworld}, enterprise work \cite{workarena,taubench},
general-assistant settings \cite{gaia,osworld}, and tool use
\cite{agentbench,agentboard,toolgym,deepresearchbench,mcpbench,mcpuniverse}.
\gittaskbench \cite{gittaskbench} belongs to the repository-grounded family but
covers a wider range of task domains---including office-document extraction, web
scraping, image processing, and speech---each graded by its own evaluator
script. Our paper does not introduce a competing benchmark; it studies how
\gittaskbench's existing official outputs should be reported.

\paragraph{Trajectory diagnosis and post-hoc analysis.}
A complementary line of work argues that final success alone is insufficient for
understanding agent behavior. \texttt{AgentRx} diagnoses agent failures from
execution trajectories \cite{agentrx}, and \texttt{TRAJEVAL} decomposes
code-agent traces into granular failure modes \cite{trajeval}. These approaches
require access to full execution logs and manual or model-based annotation. Our
starting point is earlier in the analysis pipeline: the benchmark's own official
\processmetric/\resultmetric split already reveals reportable structure before
any trajectory-level inspection begins.

\paragraph{Measurement lessons from adjacent evaluation fields.}
The concern that aggregate scores hide meaningful failure structure is not
unique to agent evaluation. Long-context research has shown that
middle-position forgetting, benchmark family variation, and evaluation
granularity all affect what an aggregate score actually measures
\cite{lostmiddle,longbench,ruler,infinitebench,nolima,loogle}. Multimodal
benchmarks have independently demonstrated that answer-channel design,
extraction quality, and thresholded criteria can shift reported outcomes
substantially \cite{mme,mmmu,mathvista,hallusionbench,blink}. Both literatures
share a lesson directly relevant to our setting: when a benchmark's evaluation
pipeline already distinguishes intermediate states, collapsing them into one
number discards diagnostically useful information.

\paragraph{Reporting-oriented evaluation and benchmark integrity.}
Evaluation infrastructures have argued for richer reporting. \texttt{HELM}
emphasizes standardized multi-scenario and multi-metric tables \cite{helm};
\texttt{Dynabench} argues that benchmarks must remain informative as models
saturate static test sets \cite{dynabench}; and \texttt{WildBench} pushes
evaluation toward harder user-originated task distributions \cite{wildbench}.
Recent work further extends this concern to agent-specific settings:
\texttt{MAPS} examines the structural integrity of multilingual agent
benchmarks \cite{maps}, \texttt{ConVerse} stresses the need for comprehensive
safety evaluation beyond global pass rates in agent-to-agent interactions
\cite{converse}, and \texttt{DebateQA} argues that evaluation metrics should
reflect the nuanced structure of the task space rather than collapsing it into
one scalar \cite{debateqa}.
Our work shares the same instinct applied to a specific benchmark: once
\gittaskbench already exposes separable success conditions through its official
\processmetric/\resultmetric fields, reporting should preserve that separation.
